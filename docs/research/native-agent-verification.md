# Research: what agents can safely do on the Swift/native side with remote-only testing

> **Status:** Current · **Date:** 2026-07-26 · **Issue:** [#147](https://github.com/dirkpostma/heart-rate-ble/issues/147)

Resolves wayfinder ticket #147 (map #146). Researched 2026-07-26 against primary
sources (Apple docs and man pages on Xcode 26.5, docs.expo.dev, the expo/expo and
facebook/react-native repos) plus **live probes on this Mac Studio** — every
timing below was measured here, headless, with no device and no EAS quota.

## TL;DR

Agents can do far more native work than "hands off Swift" would suggest. There
is a four-rung verification ladder, all headless on this Mac:

1. **Type-check in ~3 s** — `swiftc -typecheck` against the iOS simulator SDK
   catches type/symbol/availability errors in `targets/widgets/` with no
   prebuild at all.
2. **Compile the real targets in ~6 s incremental / ~3 min warm** —
   `xcodebuild build` of the `LiveActivity` pod scheme or the
   `HeartRateWidgets` scheme against `generic/platform=iOS Simulator`,
   unsigned (`CODE_SIGNING_ALLOWED=NO`). Verified exit 0 on this machine.
3. **Unit-test on the simulator** — `xcodebuild test` on a booted simulator is
   fully headless and needs zero signing assets; both XCTest and Swift Testing
   work. The repo has **no test target today**; adding one has CNG caveats
   (below), so this rung is *available but not yet built*.
4. **End-to-end on the simulator** — iOS simulators render Live Activities and
   the Dynamic Island, `simctl` can boot/install/launch/screenshot headlessly,
   and the app's built-in demo heart-rate monitor
   (`src/ble/DemoHeartRateMonitor.ts`) drives the entire
   JS → `LiveActivityModule` → ActivityKit → widget pipeline with **no BLE**.

Genuinely hands-off (device-only): anything downstream of a **real BLE strap**
(CoreBluetooth does not exist on the simulator), real-world
background/jetsam/suspension behavior (the exact class of bug in #140),
Lock-Screen/Dynamic-Island presentation *fidelity* and animation nuances, and
APNs delivery characteristics. Those stay on the TestFlight/OTA phone loop.

## The native surface, and what verifies it

| Surface | Language | Fastest full check | Verified here |
|---|---|---|---|
| `targets/widgets/*.swift` (widget + Live Activity UI) | Swift/SwiftUI | `swiftc -typecheck` (~3 s), then rung 2 | yes — see below |
| `modules/live-activity/ios/*.swift` (Expo module) | Swift + ExpoModulesCore | `xcodebuild build -scheme LiveActivity` (~6 s incremental) | yes — exit 0 |
| `plugins/*.js`, `targets/widgets/expo-target.config.js` | JS | Jest + `expo prebuild` then diff/compile the generated `ios/` | prebuild loop already proven in [local-ios-builds.md](local-ios-builds.md) |
| `shims/empty.js`, `metro.config.js` aliases | JS | Jest / Metro bundle (`npx expo export`) | JS-side, no device needed |
| generated `ios/` | — | never hand-edited; gitignored, regenerated by `npx expo prebuild --clean` ([CNG docs](https://docs.expo.dev/workflow/continuous-native-generation/)) | — |

## Rung 1 — `swiftc -typecheck`: seconds, no prebuild

Verified 2026-07-26 on this machine:

```sh
xcrun swiftc -typecheck -application-extension \
  -sdk "$(xcrun --sdk iphonesimulator --show-sdk-path)" \
  -target arm64-apple-ios16.2-simulator \
  targets/widgets/*.swift
# ~3 s, clean
```

Two traps, both hit and resolved during this research:

- **`-application-extension` is mandatory.** The widget target compiles with it
  (it's an app extension), and `HeartRateWidget.swift` guards with
  `#available(iOSApplicationExtension 17.0, *)`. Without the flag, the guard
  doesn't satisfy the checker and you get *false* availability errors on
  `containerBackground(for: .widget)`.
- `-target …ios16.2-simulator` must match `deploymentTarget` in
  `expo-target.config.js`, or availability checking is meaningless.

This works because the widget files import only SDK frameworks (SwiftUI,
WidgetKit, ActivityKit). It does **not** work for
`modules/live-activity/ios/` — `import ExpoModulesCore` needs the pod-installed
workspace, i.e. rung 2.

What the compiler alone catches: type errors, missing symbols,
protocol-conformance failures, and **API availability** — Swift statically
verifies `@available`/`if #available` against the deployment target
([Swift book, "Checking API Availability"](https://docs.swift.org/swift-book/documentation/the-swift-programming-language/controlflow/#Checking-API-Availability)).
What it cannot catch: any runtime behavior — logic bugs, authorization
failures, OS-mediated behavior, and this repo's one nasty compile-clean trap
(the duplicated-attributes invariant, below).

## Rung 2 — `xcodebuild build` per scheme: the real compile, still seconds

`xcodebuild` is Apple's headless build interface (man page;
[TN2339](https://developer.apple.com/library/archive/technotes/tn2339/_index.html)).
Simulator destinations need **no signing assets**: the `iphonesimulator` SDK
defaults to ad-hoc signing (`CODE_SIGN_IDENTITY = "-"`,
`AD_HOC_CODE_SIGNING_ALLOWED = YES`, verified in the SDK's `SDKSettings.plist`
on Xcode 26.5), which is why react-native's own CI builds and tests on
anonymous GitHub `macos-15` runners
([test-all.yml](https://github.com/facebook/react-native/blob/main/.github/workflows/test-all.yml)).

Measured on this machine (existing `ios/` from prebuild, warm DerivedData):

```sh
cd ios
# Expo module (compiles LiveActivityModule.swift + HeartRateAttributes.swift):
xcodebuild build -workspace HeartRateBLE.xcworkspace -scheme LiveActivity \
  -destination 'generic/platform=iOS Simulator' -quiet CODE_SIGNING_ALLOWED=NO
# first run ~3m20s (builds ExpoModulesCore deps), incremental ~6 s, exit 0

# Widget target (compiles everything in targets/widgets/ exactly as shipped):
xcodebuild build -workspace HeartRateBLE.xcworkspace -scheme HeartRateWidgets \
  -destination 'generic/platform=iOS Simulator' -quiet CODE_SIGNING_ALLOWED=NO
# ~3m15s warm-cache, exit 0
```

Traps, hit here:

- **Use `-workspace`, never `-project`.** The bare project can't resolve the
  `Expo`/`React` modules (verified: exit 65, 2600 errors).
- **Worktree agents:** the development pod in `ios/Pods` points at the *main
  checkout's* `modules/live-activity`. An agent in a `.claude/worktrees/…`
  worktree must run its own `npx expo prebuild` + `pod install`
  (`LANG=en_US.UTF-8`, per [local-ios-builds.md](local-ios-builds.md)) or its
  module edits are not what gets compiled.
- Config-plugin / target-config changes need `npx expo prebuild --clean` first
  (a [dangerous-mod plugin](https://docs.expo.dev/config-plugins/plugins/) like
  `withBlePlxStripCxxModules` runs during prebuild), then rung 2 confirms the
  generated project still compiles.

## Rung 3 — XCTest / Swift Testing on the simulator: viable, not yet wired up

`xcodebuild test -destination 'platform=iOS Simulator,name=iPhone 17 Pro'` runs
fully headless (RN CI, above). Swift Testing ships with Xcode 16+ and runs
through the same `xcodebuild test` path
([Apple docs](https://developer.apple.com/documentation/testing)). This Mac has
Xcode 26.5 and a fleet of iOS 26 simulators — nothing is missing except **a
test target, which this repo does not have** (`xcodebuild -list`: only
`HeartRateBLE` and `HeartRateWidgets`).

What a test target could and couldn't cover:

- **Widget extensions cannot host a test bundle.** Apple never documents this
  outright, but Apple DTS's guidance is to extract extension logic into plain
  units and test those outside the extension
  ([forums/89829](https://developer.apple.com/forums/thread/89829));
  `TimelineProvider.Context` can't even be constructed in a test
  ([forums/672442](https://developer.apple.com/forums/thread/672442)). Pattern:
  compile the Swift files into the test target too (or a shared framework) and
  test the pure parts — `LatestReading` JSON decoding, stale/date math,
  `ContentState` round-trip encoding and its 4 KB ActivityKit budget
  ([ActivityKit docs](https://developer.apple.com/documentation/activitykit/displaying-live-data-with-live-activities)).
- **`Activity.request` is not unit-testable** — it needs user authorization and
  app context (same ActivityKit doc). Integration stays at rung 4.
- **Expo has machinery but no user-facing docs for it**:
  [`expo-modules-test-core`](https://github.com/expo/expo/blob/main/packages/expo-modules-test-core/README.md)
  + CocoaPods `test_spec`s is how expo/expo tests its own Swift
  (`packages/expo-modules-core/ios/Tests/`, run by
  `.github/workflows/ios-unit-tests.yml` on macOS runners via plain
  `xcodebuild`). It would work for `modules/live-activity` in principle, but
  the SDK 57 docs document only [JS-level mocking](https://docs.expo.dev/modules/mocking/)
  — treat wiring it into a CNG app as unofficial.
- **CNG caveat for any test target:** `ios/` is disposable, so a hand-added
  test target dies on the next `prebuild --clean`. It must come from a config
  plugin / `@bacons/apple-targets` config or live outside `ios/`.
- **`swift test` (SwiftPM) is a dead end here.** SwiftPM tests target the host
  (macOS) toolchain; there is no Apple-shipped iOS Swift SDK for it
  ([SE-0387](https://github.com/swiftlang/swift-evolution/blob/main/proposals/0387-cross-compilation-destinations.md)).
  Every Swift file in this repo imports ActivityKit, WidgetKit or
  ExpoModulesCore — none of which exist on macOS — so `swift test` applies only
  if pure logic were first extracted into a platform-free package, and today
  there is barely any such logic (a ms→`Date` conversion).

**Verdict:** rung 3 is real but is its own small project (config-plugin-managed
test target). Until someone builds it, agents verify with rungs 1–2 + rung 4.

## Rung 4 — simulator end-to-end: the surprise headroom

- **Live Activities render in the simulator** (Dynamic Island included) since
  the Xcode 14.1 / iOS 16.1 generation
  ([Xcode 14.1 release notes](https://developer.apple.com/documentation/xcode-release-notes/xcode-14_1-release-notes)
  list a fix for "iOS simulators may stop showing Live Activities and Dynamic
  Island features").
- **`simctl` is fully headless**: `boot`, `install`, `launch`, `openurl`,
  `push`, `status_bar`, `io <udid> screenshot` (verified locally, Xcode 26.5).
  An agent can build the app for the simulator, install, launch, drive it, and
  capture Lock-Screen/Island screenshots without any GUI.
- **The BLE gap is already bridged in-app**: `DemoHeartRateMonitor`
  (resting/workout/dropout profiles, wired through `appStore` and
  `DemoSurface`) feeds the same store the real strap does — so
  start/update/stale/end of the Live Activity, the `endAfter` grace path from
  #140, and widget rendering are all exercisable on a simulator with zero
  hardware.
- **APNs nuance** (future, if push-to-start ever lands): `simctl push` cannot
  send `liveactivity`-type pushes ("Only application remote push notifications
  are supported", `simctl help push`), but Apple explicitly supports **real
  sandbox APNs to the simulator** on Apple silicon Macs
  ([ActivityKit push docs](https://developer.apple.com/documentation/activitykit/starting-and-updating-live-activities-with-activitykit-push-notifications)).
  This Mac Studio qualifies.

## Hands-off: what no headless setup can verify

1. **Real BLE.** "Simulator does not support the use of Bluetooth devices"
   (Apple Developer Tools engineer,
   [forums/14983](https://developer.apple.com/forums/thread/14983); the old
   USB-dongle technote [TN2295](https://developer.apple.com/library/archive/technotes/tn2295/_index.html)
   is retired). Pairing, reconnect timing, RSSI, real strap quirks — device
   only. Agents may refactor *around* `react-native-ble-plx` usage (it's JS
   anyway), but anything that changes BLE behavior needs the phone.
2. **Background execution / suspension / jetsam.** The #140 bug class (JS
   timers dying on suspension) and the SDK 57 Hermes memory-pressure kills are
   real-device phenomena; the simulator does not reproduce iOS scheduling or
   memory pressure faithfully.
3. **Presentation fidelity.** Simulator screenshots prove layout and data flow;
   they do not prove Dynamic Island animation feel, `.pulse` symbol-effect
   rendering on device, Always-On-Display dimming, or Lock Screen behavior
   under real conditions. Treat sim screenshots as regression evidence, not
   final sign-off.
4. **Signing/entitlements/TestFlight behavior.** Unsigned simulator builds
   bypass the entire provisioning story; app-group entitlements *resolution*,
   ad hoc profiles, and ASC processing verify only via the existing release
   loop ([local-ios-builds.md](local-ios-builds.md), [release-operations.md](../release-operations.md)).

### Repo-specific trap that compiles clean

`HeartRateAttributes` is **intentionally duplicated**
(`modules/live-activity/ios/` vs `targets/widgets/`) because a pod can't share
source with an Xcode target; ActivityKit matches app↔extension by the type's
*name and encoding*. Drift between the copies compiles perfectly in both
targets and silently breaks the Live Activity at runtime. Any agent touching
either file must change both identically (`diff` them — today they differ only
in comments) and should confirm on the simulator via demo mode. This is the
canonical example of why "it compiles" is necessary but not sufficient here.

## Policy this supports (for the decision ticket)

- **Green (verify with rungs 1–2, optionally 4):** Swift refactors that
  preserve behavior — extracting views/helpers, renames, dead-code removal,
  comment/doc work, availability-guard cleanups, `Theme.swift` palette sync;
  module-level refactors in `LiveActivityModule.swift` that keep the
  ActivityKit call shapes; config-plugin and target-config changes (prebuild +
  compile the result).
- **Yellow (rung 4 mandatory — simulator run with demo mode + screenshots):**
  any change to Live Activity/widget *content or state logic* (stale handling,
  dismissal policies, layout), `HeartRateAttributes` changes (both copies,
  identically), timeline-provider logic.
- **Red (hands-off without a human + phone in the loop):** BLE behavior,
  background/suspension semantics, anything whose acceptance criterion is "how
  it looks/feels on the island/AOD", signing/entitlement changes destined for
  TestFlight.
